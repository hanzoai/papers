\begin{abstract}
\noindent
We describe a retrieval design for a merge-based column store whose rows carry
sparse representations over a mixed basis --- words, entities, code symbols,
learned concepts, relations and structural motifs --- alongside dense
embeddings, and we specify how its cost is to be measured. The index is a
weighted inverted file: one posting list per basis element, holding a row
identifier and a weight, so a query written over the same basis is scored only
over the posting lists of the basis elements it activates, with top-$k$
evaluation under block-max pruning. Above it sits a routing structure built per
MergeTree part --- regions described by a centroid, a covering radius, the
maximum weight each basis element reaches inside the region, and counting
statistics --- aggregated into a table-level structure the planner consults to
exclude parts before any per-part index is searched, including the per-part
approximate-nearest-neighbour graph a column store already builds.

Most of the parts are established, and we say which. Weighted inverted files
with dynamic pruning, cluster- and shard-level routing by collection
statistics, covering-radius bounds from metric indexes, and per-segment vector
indexes are prior art. What is proposed here is their arrangement inside the
part lifecycle of a merge-based store: one weighted index over a heterogeneous
basis, block maxima aligned to granules, region summaries that merge when parts
merge, and selection of parts by an upper bound on the score they can still
contribute before any approximate search runs.

The claim we intend to test is narrow. At a fixed query distribution and a
fixed recall target, expected retrieval cost should grow with the size of the
relevant neighbourhood rather than with the size of the corpus. It is not a
worst-case guarantee: a query whose relevant set is the whole corpus costs time
linear in the corpus, under this design and under any other. The protocol fits
$C(N) = aN^{\alpha}$ to parts, granules and bytes touched at a held recall
target, and reports bytes fetched per correct answer, recall@$k$ and latency
percentiles across corpus sizes, against upstream ClickHouse as the baseline.
This version reports no measurements. The baseline lane is only starting, and
every cell in the results section is a placeholder until it writes one.
\end{abstract}
